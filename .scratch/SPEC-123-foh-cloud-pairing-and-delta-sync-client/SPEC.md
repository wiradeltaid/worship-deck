## 1. Problem Statement & Motivation

WorshipDeck v0.2.0 is a self-contained, zero-dependency desktop application running an embedded Go HTTP API and SQLite database. Under **ODR-019** ("Arsitektur SaaS Hybrid Multi-Tenant dan Model Monetisasi WorshipDeck"), the product operates under the core doctrine:

> **"Cloud Prep, Offline Stage"**
> - *Monday through Saturday*: The worship and media team prepares song lyrics, Bible verses, announcements, and sermon graphics collaboratively in the cloud (`https://{slug}.worshipdeck.org`).
> - *Sunday Morning*: The FOH operator at the sanctuary multimedia booth presses a single button `[ ⇅ Sync from Cloud ]` on the desktop app (`worship-deck --desktop`), pulling all database mutations and high-resolution media assets into local storage.
> - *During the Service*: The entire sanctuary presentation runs 100% offline from the local SQLite database and local disk uploads. Even if the venue router is unplugged, the Sunday service proceeds without interruption.

Prior to SPEC-123, cross-instance sync (`UC-32`, `FR-40`, `SPEC-47`) remained experimental, restricted to same-origin testing or ephemeral token paste, without:
1. A permanent, secure pairing mechanism between a church's cloud instance and physical FOH laptop.
2. Safe local credential storage outside the git tree in `%LOCALAPPDATA%\WorshipDeck\pairing.json`.
3. Automated asset streaming and SHA-256 checksum verification for media files.
4. An absolute **In-Flight Service Freeze** invariant protecting live Sunday worship from sudden background mutations or slide shifts.
5. An intuitive visual pairing modal and stage readiness indicator (`🟢 SIAP IBADAH MINGGU`).

SPEC-123 closes this operational gap by engineering a production-grade FOH Cloud Pairing & Delta Sync Client.

## 2. Technical Architecture & Invariant Specifications

### 2.1 Pairing Handshake & Secure Local Credential Storage
1. **Token Format & Validation (K1-02)**:
   - The FOH Pairing Token is generated by the SaaS Control Plane (`wiradelta-admin` via ODR-019 §3.4) with format:
     `foh_<tenant_id_or_device_id>.<random_secret_base64url>` (32 bytes cryptographic random, base64url unpadded).
   - Format is strictly validated with regex:
     `^foh_([A-Za-z0-9_-]{1,128})\.([A-Za-z0-9_-]{43})$`.
   - Token is treated as an opaque bearer credential; ID in prefix is not trusted without server handshake.
2. **Local Storage Contract (K1-01, K1-04)**:
   - The pairing configuration schema:
     ```go
     type PairingConfig struct {
         Version    int       `json:"version"` // 1
         CloudURL   string    `json:"cloud_url"`
         TenantID   string    `json:"tenant_id"`
         DeviceID   string    `json:"device_id,omitempty"`
         Token      string    `json:"token"`
         PairedAt   time.Time `json:"paired_at"`
     }
     ```
   - Cursors and revisions MUST be stored in SQLite with replica state, NEVER in `pairing.json`.
   - Stored strictly in application mutable data directory resolved via `desktop.ResolveDataDir`:
     `filepath.Join(dataDir, "pairing.json")` (on Windows desktop: `%LOCALAPPDATA%\WorshipDeck\pairing.json`).
   - File permissions: `0600` on Unix; on Windows, enforced with protected DACL (owner & system principals only, no other local users).
   - Publication uses atomic replacement via temporary file `.tmp_pairing_<nonce>`.
   - Invariant: `pairing.json` MUST NEVER be stored in repository root or tracked by git (`tests/public-repo-guard.test.mjs`).
3. **Desktop Pairing Endpoints (Local Go API) (K1-05)**:
   - `GET /api/desktop/pairing`: Returns safe DTO with `Cache-Control: no-store`:
     ```json
     {
       "paired": true,
       "cloud_url": "https://gereja-anda.worshipdeck.org",
       "tenant_id": "tenant_01J9X4T7M5",
       "church_name": "Gereja Contoh Sintetis",
       "paired_at": "2026-10-18T06:45:00Z",
       "token_masked": "foh_01J9X4T7M5.********"
     }
     ```
   - `POST /api/desktop/pairing`: Handshake endpoint. Takes `{ "cloud_url": "...", "token": "..." }`, validates syntax, executes authenticated handshake to remote `/api/sync/status`, verifies tenant binding and capabilities, atomically saves `pairing.json`, and returns success.
   - `DELETE /api/desktop/pairing`: Unpairs the device and securely removes `pairing.json`. Does NOT delete existing local database/media snapshots (local content remains presentation-ready).

### 2.2 Delta Sync Engine & Media Asset Streaming with SHA-256 Checksums (K2-01..K3-02)
1. **Delta Pull Protocol & SQLite Transaction Atomicity (K2-01, K2-02, K2-03)**:
   - Endpoint: `POST /api/desktop/sync/pull-cloud` triggered by operator or scheduled sync.
   - Resolves remote instance URL and bearer token from `pairing.json`.
   - Checks local dirty state: if unsynced local emergency edits exist, rejects with `409 local_changes_pending` (K2-04).
   - Fetches batch delta from remote `{cloud_url}/api/sync/pull` outside of SQLite transaction.
   - Downloads & verifies all required media assets first (K3-01).
   - Opens local SQLite write transaction with `BEGIN IMMEDIATE` and `foreign_keys=ON`.
   - Applies mutations (`services`, `hymns`, `song_set_entries`, `background_library_images`, `announcement_sets`, `announcement_set_slides`, `artifact_templates`, `service_registry_snapshots`, `song_set_layouts`) honoring parent-child foreign keys.
   - Commits mutations and updates cursor/revision in the SAME transaction.
2. **Media Asset Streaming with Incremental SHA-256 Checksums (K3-01, K3-02)**:
   - Streams asset from remote `/api/sync/assets/download?hash={hash}` directly to temporary file `uploads/.tmp_{hash}_{nonce}`.
   - Calculates SHA-256 on the fly using `io.TeeReader` and `crypto/sha256`.
   - Atomically renames to `uploads/{hash}.{ext}` only if byte count and digest strictly match.
   - Corrupted or interrupted transfers immediately delete temporary file and fail the batch without advancing cursor.
3. **Telemetry & Audit**:
   - Records sync execution summary: `{ "ok": true, "services_count": 2, "hymns_count": 45, "assets_downloaded": 12, "bytes_transferred": 18459200, "duration_ms": 3410 }`.

### 2.3 In-Flight Service Freeze Invariant & Concurrency Guard (K-FREEZE-01, K4-02, K4-03)
1. **Sunday Stage Freeze Rule**:
   - When a service is actively being presented (`/projector`, `/slideshow`, or live presentation session active):
     `F(t) => Psync(t) forbidden`.
   - `TryAcquireSyncLock` enforces mutual exclusion:
     - If presenter is live: sync calls are immediately rejected with `409 Conflict`:
       ```json
       {
         "error": {
           "code": "presenter_active",
           "message": "Sinkronisasi ditahan selama sesi presentasi."
         }
       }
       ```
     - If sync is active: presenter start is held or rejected with `409 sync_in_progress`.
2. **Defect Injection Proofs (K4-04)**:
   - Proves red-to-green: mutating presenter lock state immediately refuses sync before any network or file I/O occurs.

### 2.4 FOH UI: Pairing Modal & Stage Readiness Status Indicator (Opus UI/UX)
1. **Cloud Workplace Pairing Modal (CloudPairingModal component)**:
   - Form inputs: Workspace Address (`https://gereja-anda.worshipdeck.org`) and Pairing Token (`foh_...`).
   - Guidance card: Step-by-step instructions referencing `console.worshipdeck.org`.
   - Two-stage button gate: `[ Hubungkan / Connect ]` button remains disabled until `[ Uji koneksi / Test connection ]` succeeds and displays the church name.
   - Connected state displays church badge, instance address, connection date, and `[ Putuskan hubungan / Disconnect ]` button with confirmation dialog. Disconnecting does not delete local data.
2. **Stage Readiness Indicator Badge (FohSyncIndicator component)**:
   - Anchored in FOH Operator Shell header with 9 defined states:
     - **S1 (Hijau)**: `Siap ibadah` · *Sinkron Min 07.42 · 8 aset terverifikasi*
     - **S1b (Hijau titik abu)**: `Siap ibadah` · *Memakai sinkron Min 07.42 · cloud tidak terjangkau*
     - **S2 (Amber)**: `Ada pembaruan di cloud` · *Sinkron terakhir Sab 20.15*
     - **S2b (Amber)**: `Belum disinkronkan` · *Tarik data ibadah sebelum tayang*
     - **S3 (Amber)**: `Sinkron belum tuntas` · *Memakai data Sab 20.15*
     - **S4 (Merah)**: `Perlu perhatian` · *Akses laptop dicabut / Aset hilang di laptop*
     - **S5 (Biru spinner)**: `Menyinkronkan…` · *Aset 3 dari 8 · 124 dari 310 MB*
     - **S6 (Ungu lock)**: `Panggung tayang` · *Sinkron dijeda*
     - **S0 (Abu-abu)**: `Belum terhubung ke cloud` · *Konten lokal tetap bisa ditayangkan*
   - Action Button: `[ ↓ Sinkronkan dari cloud ]` / `[ ↓ Sync from cloud ]` with byte-based progress feedback and calming error messages.
